# Skill：论文阅读笔记撰写流程

## 适用场景

用于撰写论文的阅读笔记。

目标不是简单翻译论文，而是形成一份适合后续研究复盘、模型设计参考、PPT 汇报和 related work 整理的结构化笔记。

最终笔记先在开头添加论文信息块，再进入正文。正文固定包含 4 个部分：

```markdown
# 0. 实验
# 1. 论文核心问题
# 2. 论文贡献
# 3. 模型流程说明
```

## 总体写作原则

- 开头论文信息块放在 `# 0. 实验` 之前，使用紧凑列表，不新增正文一级标题。
- 正文结构固定为 4 个部分，不额外增加一级大标题。
- 根据正式发表类型选择期刊或会议信息模板；等级、指标和代码状态需核实，记录数据年份、来源和查询日期。
- 实验部分主要写消融实验，不展开完整主实验、参数实验、效率实验。
- 论文核心问题部分说明文章解决什么问题，不写成模型流程。
- 论文贡献部分主要根据引言中的 contribution 原文进行翻译整理。
- 模型流程说明是重点，需要清晰说明输入特征、组件、信息流、预测方式、loss 和关键设计理解。
- 可以加入个人理解，尤其是在消融实验结论、模型流程关键设计、值得注意的地方中。
- 输出默认是 Obsidian 兼容 Markdown，需要同时满足紧凑排版和渲染边界安全。

## 开头论文信息块

### 1. 发表类型判定

- 先检查论文首页、DOI 对应的出版社页面或正式会议论文记录，确认发表类型、载体名称和发表年份。
- 期刊论文使用期刊模板；会议论文使用会议模板，并区分主会、Workshop 或其他实际发表轨道。
- 只有预印本或无法确认正式发表信息时，标注“预印本 / 正式发表信息待核实”，不套用期刊或会议等级。
- 期刊论文在会议上展示等情况，按正式出版载体填写；同一工作有多个版本时，注明当前阅读版本，避免混用不同版本的信息。

### 2. 期刊论文模板

以下为占位模板，生成笔记时必须填入核实结果；缺失字段按后文规则注明状态。

```markdown
- **期刊名称**：期刊全称（简称），发表年份；[论文页面](论文页面地址)
- **期刊等级**：JCR QX（学科类别，数据年份）；中科院 X 区（大类名称，分区版本年份）；[分区来源](来源地址)
- **影响因子**：X.XX（JIF 数据年份）；[指标来源](来源地址)
- **是否开源**：是；[作者官方代码仓库](仓库地址)
- **查询日期**：YYYY-MM-DD

# 0. 实验
```

### 3. 会议论文模板

```markdown
- **会议名称**：会议全称（简称），会议年份；主会 / Workshop / 其他轨道；[论文页面](论文页面地址)
- **会议级别**：CCF A / B / C 类（目录版本年份）；顶会认定：是 / 否 / 未核实（所属领域与依据）；[评级来源](来源地址)
- **是否开源**：是；[作者官方代码仓库](仓库地址)
- **查询日期**：YYYY-MM-DD

# 0. 实验
```

如为预印本或发表信息待核实，开头改为“发表类型”“发表信息”“是否开源”“查询日期”四行；已确认的预印本平台和论文链接可以保留，期刊与会议等级不适用。

### 4. 等级、指标与来源核验

- 生成笔记时联网核验这些信息，不凭记忆填入分区、影响因子、CCF 等级或仓库状态。优先使用出版社、正式会议记录、指标发布机构、CCF 官方目录及作者官方页面；公开检索使用论文标题、作者、载体名称或方法名称。
- 默认采用查询时最新可核实的数据，并注明数据年份或目录版本年份；用户指定发表当年或其他年份时，按指定年份查询。发表年份、指标数据年份和查询日期分别记录，不能互相替代。
- JCR 分区写明学科类别；若属于多个类别，分别列出各类别及其分区，不只选最高分区。无法取得全部类别时，说明核实范围。
- 中科院分区默认写大类及其名称，并注明分区版本年份；来源区分版本口径时，保留口径说明。需要时补充小类分区，并明确标注大类、小类。
- 影响因子使用 Journal Impact Factor（JIF），注明指标对应的数据年份，不以 CiteScore、五年影响因子或其他指标代替。来源只有发布年份时，说明发布年份及数据年份是否已核实。
- CCF 等级依据对应版本的官方目录填写；确认未收录时写“CCF 未收录（目录版本年份）”，不能把无法查询写成未收录。
- “是否属于顶会”与 CCF 分级分别判断：写明所属领域和可核实依据；只有 CCF 等级证据时，保留该等级，顶会认定写“未单独核实”，不自动推出顶会结论。
- Workshop 或其他轨道不能直接沿用主会等级；查明实际轨道是否适用该评级，无法确认时注明“该轨道评级未核实”。
- 无法核实的字段写“未核实”并简要说明原因；没有对应指标时，经核实后写“暂无该指标”或“不适用”。可核实部分先填，不影响正文笔记继续生成。
- 来源链接直接附在对应字段后；不同类别、评级或指标来源不同，分别附对应链接。无法直接访问官方数据、使用公开转引时，注明转引来源和所引年份，不将其写成已直接核实官方数据。

### 5. 代码公开状态判定

“是否开源”指本文方法的代码公开情况。论文开放获取、PDF 免费可读或仅公开数据、模型权重，不能单独作为代码开源的依据。

先检查论文中的代码声明和链接、论文官方页面及作者项目页面，再按论文标题 / 方法名称结合作者信息检索代码仓库。打开候选仓库，核对其与当前论文的对应关系、官方身份和是否包含本文实现；只有项目介绍、空仓库或“coming soon”时，不写成已开源。

| 核验情况 | “是否开源”字段写法 |
|---|---|
| 作者官方代码仓库可访问且包含本文实现 | 是；给出作者官方仓库地址 |
| 完成上述检索后未发现作者公开代码 | 否（截至查询日期未发现作者公开代码） |
| 论文声明开源并给出地址，但原仓库无法访问 | 论文声明开源，但原仓库目前无法访问；保留原地址，说明观察到的状态 |
| 论文声明开源，但检索后未找到可访问的官方仓库 | 论文声明开源，但未找到可访问的官方仓库 |
| 作者表示未来发布，或官方仓库尚无实现 | 暂未开源（说明将发布 / 空仓库 / 仅项目介绍等情况）；保留已有项目地址 |
| 原地址失效，但找到作者官方迁移地址 | 是；给出当前地址，并注明原地址已失效及官方迁移依据 |
| 官方仓库已归档，但代码仍可访问 | 是；给出地址，并注明仓库已归档 |
| 只有第三方复现 | 否（未发现作者官方代码）；另附第三方复现地址并明确身份 |
| 网络、权限或工具限制导致无法完成核验 | 未核实；说明原因，保留论文提供的代码地址 |

- 出现 404 或访问失败时写“无法访问”，不直接断言仓库已删除；除非有作者公告等明确证据。
- 代码已公开但未见开源许可证时，写“代码公开，未见开源许可证”，并给出地址，不推断其授权范围。
- 只公开部分实现时，注明实际公开范围，不写成完整实现已公开；仅有数据或权重时，单独说明这些材料，代码状态仍按上表判定。

### 6. 论文信息块输出检查

- 信息块是否位于 `# 0. 实验` 之前，并与正文之间保留一个空行。
- 是否按当前阅读版本的正式发表类型选择模板，名称、年份及会议轨道是否对应。
- 必填字段是否都有核实结果或明确状态，期刊等级是否区分 JCR 与中科院分区。
- 分区、JIF 和 CCF 等级是否注明数据年份、目录版本或口径，来源是否支持对应结论。
- 顶会认定是否给出领域与依据，Workshop 是否避免直接套用主会评级。
- 代码链接是否实际打开并核对论文身份，声明开源但仓库不可用、未找到仓库、部分公开和第三方复现是否如实说明。
- 是否保留查询日期，是否清除了模板占位符和不适用的候选项；无法核实时是否使用“未核实”而非猜测。

# 0. 实验

## 写作范围

实验部分主要说明文章的消融实验，不展开主实验、超参数实验、效率实验等内容。

除非这些内容与消融实验直接相关，否则不要单独写：
- 主实验结果；
- baseline 全面对比；
- 超参数分析；
- 训练/测试效率；
- 数据集统计；
- 指标定义。

## 写作重点

实验部分需要回答：
1. 文章做了哪些消融实验；
2. 每个消融变体去掉或替换了什么；
3. 消融结果说明了什么；
4. 哪些地方值得注意。

## 推荐结构

```markdown
# 0. 实验

这一部分主要说明文章的消融实验。文章的消融实验主要围绕 XXX、XXX、XXX 几个核心设计展开。

## 0.1 消融实验内容

- **variant A**：说明去掉/替换了什么。
- **variant B**：说明去掉/替换了什么。
- **variant C**：说明去掉/替换了什么。

## 0.2 消融实验结果的个人理解

从结果来看，最关键的结论不是简单地说“所有模块都有用”，而是……

第一，……

第二，……

第三，……

## 0.3 值得注意的地方

我觉得这里最值得注意的是……

整体来看，真正支撑模型效果的应该是：

> XXX + XXX + XXX。
```

## 写作风格

消融实验结论部分可以使用个人理解式写法，不需要严格按照文章原文总结。

重点是简要、清晰、有判断。

可以使用这样的表达：

```markdown
从结果来看，最关键的结论不是“每个模块都有用”，而是模型的主要增益来自 XXX 和 XXX。
```

```markdown
这个消融结果说明，XXX 不是简单作为附属特征加入，而是应该被作为具有独立结构的信息来建模。
```

如果某个消融提升很小，需要指出：

```markdown
这个模块虽然有效，但从消融幅度来看，它更像是辅助增强项，而不是模型最核心的性能来源。
```

## 注意事项

- 不要把实验部分写成完整实验复述。
- 不要展开主实验表格。
- 不要把所有指标都详细抄一遍。
- 如果文章没有明确消融实验，需要说明“文章没有提供严格消融实验”，然后只概括与模块有效性相关的实验。

# 1. 论文核心问题

## 写作目标

这一部分说明论文到底在解决什么问题。

不要只是翻译摘要，而要提炼出：
- 现有方法的不足；
- 作者认为任务中的核心矛盾；
- 为什么需要提出新模型；
- 文章的建模出发点。

## 推荐结构

```markdown
# 1. 论文核心问题

这篇论文的核心问题是：……

更具体地说，文章指出现有方法主要存在两个/三个问题。

## 1.1 问题一：XXX

说明现有方法怎么做；说明为什么这样做有问题；说明作者认为应该如何处理。

## 1.2 问题二：XXX

说明现有方法忽略了什么；说明这个因素为什么重要；说明本文如何看待这个问题。

## 1.3 核心问题总结

这篇文章的核心问题可以总结为：

> ……
```

## 写作风格

这一部分要比贡献部分更偏分析。

可以使用这样的表达：

```markdown
这篇文章的核心不是“多引入了某个特征”，而是提出了一个更明确的建模观点：

> XXX 不应该只是作为 XXX 的附属属性，而应该被作为 XXX 来建模。
```

## 注意事项

- 不要把论文核心问题写成模型流程。
- 这里重点是“为什么要做”，不是“怎么做”。
- 如果论文的动机写得比较散，需要根据摘要、引言和方法开头综合归纳。

# 2. 论文贡献

## 写作目标

这一部分主要来自论文引言部分。

如果论文中明确写了：

```text
The main contributions are summarized as follows:
```

则直接将对应贡献点翻译整理即可。

## 写作原则

- 贡献部分要忠实原文，不要加入太多个人发挥。
- 可以适度整理语言，但不要改变原文含义。
- 如果贡献点中包含方法名称，需要保留原名并解释其中文含义。

## 推荐结构

```markdown
# 2. 论文贡献

文章在引言部分明确列出了几点贡献。这里基本按照原文含义翻译整理。

## 2.1 贡献一：XXX

作者指出/提出/设计了……

## 2.2 贡献二：XXX

作者提出了……

## 2.3 贡献三：XXX

作者设计了……

## 2.4 贡献四：XXX

作者在……上进行了实验，结果表明……
```

## 注意事项

- 贡献部分不要写得太长。
- 不要在贡献部分展开详细模型分析，模型细节放到第 3 部分。
- 如果贡献和论文核心问题重复，可以简要写，不需要重新解释一遍。

# 3. 模型流程说明

## 写作目标

这是整篇阅读笔记中最重要的部分。

需要清晰、详细地说明模型流程，包括：
- 输入特征；
- embedding 方式；
- 模型组件；
- 各组件输入与输出；
- 组件之间如何连接；
- 预测方式；
- loss；
- 值得注意的关键设计；
- 必要的个人理解。

## 推荐总体写法

先用一段话概括整体流程：

```markdown
模型的整体流程可以概括为：

> 输入用户历史轨迹后，模型先……；然后……；接着……；最后……。
```

然后按照模型原文的模块划分逐步说明。

## 推荐结构

```markdown
# 3. 模型流程说明

模型整体流程可以概括为：……

文章将模型分为几个主要组件：
1. XXX；
2. XXX；
3. XXX；
4. XXX。

下面具体说明。

## 3.1 输入与任务定义

说明每条样本包含什么；用户轨迹如何定义；任务目标是什么。

## 3.2 特征与嵌入表示

说明 user、POI、region、time、category、多模态等特征如何 embedding。

### 3.2.1 用户和 POI 表示

……

### 3.2.2 region/category/time 表示

……

## 3.3 核心模块一

说明该模块的作用；说明输入；说明计算方式；说明输出；说明个人理解。

## 3.4 核心模块二

同上。

## 3.5 预测与融合

说明最终如何预测；是分类头、内积、MLP、score-level fusion 还是多任务预测；是否使用目标时间 query；是否使用辅助任务。

## 3.6 损失函数

说明主任务 loss；辅助任务 loss；多任务组合方式。

## 3.7 模型流程总结

用流程图式文字总结整个信息流。

## 3.8 值得注意的关键点

总结模型真正有效的地方；指出需要警惕的地方；说明对自己研究的启发。
```

## 特征说明要求

模型流程部分一定要写清楚特征。

例如：

```markdown
每条 check-in 可以表示为 $c=(u,p,r,t)$，其中 $u$ 表示用户，$p$ 表示 POI，$r$ 表示 region，$t$ 表示时间。
```

如果论文中使用了 region，需要说明 region 是如何得到的：

```markdown
这里的 region 不是行政区划，而是通过对 POI 经纬度进行 k-means 聚类得到的空间区域。
```

如果使用了目标时间，需要明确指出：

```markdown
POI prediction 使用了下一次访问的 ground truth time 作为 query，因此它属于 target-time-aware 的预测方式。
```

## 模块说明要求

每个模块尽量按照下面格式写：

```markdown
这个模块的目标是：

> ……

输入是……

处理方式是……

输出是……

个人理解是：

> ……
```

## 个人理解的加入位置

个人理解可以放在两个地方：
1. 模块内部，用于解释关键设计；
2. 最后总结小节，用于总结模型真正有效的机制和对当前研究的启发。

例如：

```markdown
个人理解是，这一步不是简单地加入用户向量，而是让用户偏好参与历史信息筛选。
```

```markdown
我觉得这篇文章最关键的地方不是结构复杂，而是它提出了一个明确的建模拆分：……
```

## 注意事项

- 模型流程说明要清晰，但不要写成代码级流水账。
- 公式可以保留，但公式不是重点。重点是解释公式的作用。
- 不要只写公式，还要说明公式在模型中的功能。

例如，不要只写：

```markdown
$$
h_i = \tanh(W_e e_i + W_h h_{i-1} + b)
$$
```

还要说明：

```markdown
这一步得到每个时间步的基础 RNN hidden state，后续还会基于时间间隔、空间距离和用户偏好对历史 hidden states 进行加权聚合。
```

# Obsidian 公式格式要求

论文笔记默认输出为 Obsidian 兼容 Markdown。模型流程说明中凡涉及公式、变量、embedding 维度、矩阵表达、数据 pipeline、计算流程、loss 等内容，统一使用 Obsidian 适配的 LaTeX 格式。

## 1. 行内公式

短公式、变量、符号说明使用行内公式 `$...$`。

推荐写法：

```markdown
每条 check-in 可以表示为 $c=(u,p,r,t)$，其中 $u$ 表示用户，$p$ 表示 POI，$r$ 表示 region，$t$ 表示时间。
```

## 2. 独立公式

较长公式、核心计算公式、loss、模型更新公式使用独立公式块 `$$...$$`。

推荐写法：

```markdown
用户轨迹可以表示为：

$$
T_u = \{c_1,c_2,\dots,c_v\}
$$
```

## 3. 不要用代码块写公式

不要使用代码块包裹公式。

不推荐写法：

```text
c = (u, p, r, t)
```

推荐写法：

```markdown
$$
c=(u,p,r,t)
$$
```

## 4. 数据 pipeline 的表达

数据 pipeline 可以用文字流程，也可以用独立公式表达。

推荐写法：

```markdown
整体信息流可以概括为：

$$
(u,p,r,t)
\rightarrow
(e^u,e^p,e^r,e^t)
\rightarrow
(H^p,H^r)
\rightarrow
\hat{y}_p
$$
```

也可以使用普通文本流程，但其中变量仍然使用行内公式：

```markdown
用户轨迹 $(u,p,r,t)$ 先经过 Context Embedding，得到 $(e^u,e^p,e^r,e^t)$，然后分别输入 POI 分支和 region 分支。
```

# Obsidian Markdown 紧凑排版规则

输出 Markdown 时必须采用紧凑排版，避免每行内容之间都插入空行，导致笔记上下过松。

## 1. 标题与正文

标题与正文之间保留一个空行。

推荐写法：

```markdown
## 3.1 输入特征

每条 check-in 可以表示为 $c=(u,p,r,t)$，其中 $u$ 表示用户，$p$ 表示 POI，$r$ 表示 region，$t$ 表示时间。
```

不同自然段之间保留一个空行，但不要把每句话都拆成独立段落。

不推荐写法：

```markdown
每条 check-in 可以表示为 $c=(u,p,r,t)$。

其中 $u$ 表示用户。

$p$ 表示 POI。

$r$ 表示 region。

$t$ 表示时间。
```

推荐写法：

```markdown
每条 check-in 可以表示为 $c=(u,p,r,t)$，其中 $u$ 表示用户，$p$ 表示 POI，$r$ 表示 region，$t$ 表示时间。
```

## 3. 列表内部

同一个列表内部不要在列表项之间插入空行。

不推荐写法：

```markdown
- POI 分支用于建模细粒度位置转移。

- region 分支用于建模粗粒度空间转移。

- time 主要作为辅助上下文参与偏好调制。
```


## 4. 列表结束后

列表结束后，如果继续写普通正文，需要空一行，明确结束列表块。

推荐写法：

```markdown
- POI 分支用于建模细粒度位置转移。

因此，模型的核心不是简单特征拼接，而是不同粒度信息的解耦建模。
```

# Obsidian Markdown 渲染边界规则

可以正常使用标题、列表、引用、加粗、分隔线、公式等 Markdown 语法，但必须保证不同语法块之间的边界清晰，避免 Obsidian 产生非预期渲染。

重点不是禁用 Markdown 符号，而是保证块级语法边界清晰。

## 1. 引用块后必须空一行再写正文

如果使用引用块 `>`，引用结束后必须空一行，再继续普通正文。

推荐写法：

```markdown
> 这是一段引用内容。

这是引用之外的正文。
```

不推荐写法：

```markdown
> 这是一段引用内容。
这是普通正文。
```

原因：在 Obsidian 中，如果引用块后不空行，下一行可能仍然被视为引用块的一部分，导致普通正文也被渲染成引用。

## 2. 分隔线 `---` 前后必须空一行

如果使用分隔线 `---`，它前后都必须保留空行，不能紧贴加粗、引用、公式、列表或其他 Markdown 控制符。

推荐写法：

```markdown
**小结**

---

下面进入下一部分。
```

不推荐写法：

```markdown
**小结**
---

下面进入下一部分。
```

原因：当 `---` 与上一行 Markdown 控制符紧贴时，可能无法按预期渲染为分隔线，或者与上一行语法产生冲突。

## 3. 公式块前后必须空一行

独立公式块 `$$...$$` 前后必须空一行，不能紧贴标题、列表、引用、加粗或普通正文。

推荐写法：

```markdown
模型的预测概率定义为：

$$
p(k|r_i)=
\frac{\exp(\operatorname{sim}(c_k,z_i^k))}
{\sum_{k'} \exp(\operatorname{sim}(c_{k'},z_i^{k'}))}
$$

其中，$c_k$ 表示第 $k$ 个类别原型。
```

不推荐写法：

```markdown
模型的预测概率定义为：
$$
p(k|r_i)=
\frac{\exp(\operatorname{sim}(c_k,z_i^k))}
{\sum_{k'} \exp(\operatorname{sim}(c_{k'},z_i^{k'}))}
$$
其中，$c_k$ 表示第 $k$ 个类别原型。
```

## 4. 公式块内部必须保持纯 LaTeX

公式块内部不要混入 Markdown 标题、引用、列表、分隔线或加粗符号。

不推荐写法：

```markdown
# $$
p(k|r_i)

\frac
{\exp(sim(c_k,z_i^k))}
{\sum_{k'} \exp(sim(c_{k'},z_i^{k'}))}
$$
```

推荐写法：

```markdown
$$
p(k|r_i)=
\frac{\exp(\operatorname{sim}(c_k,z_i^k))}
{\sum_{k'} \exp(\operatorname{sim}(c_{k'},z_i^{k'}))}
$$
```

## 5. 复杂公式不要拆成容易触发 Markdown 规则的碎片

复杂公式应尽量写在同一个 LaTeX 环境中，不要把 `\frac`、分子、分母拆成多个普通 Markdown 段落。

推荐写法：

```markdown
$$
p(k|r_i)=
\frac{\exp(\operatorname{sim}(c_k,z_i^k))}
{\sum_{k'} \exp(\operatorname{sim}(c_{k'},z_i^{k'}))}
$$
```

不推荐写法：

```markdown
$$
p(k|r_i)

\frac
{\exp(sim(c_k,z_i^k))}
{\sum_{k'} \exp(sim(c_{k'},z_i^{k'}))}
$$
```

## 6. 加粗与其他块级语法之间要注意边界

加粗可以正常使用，但如果加粗行后面紧接分隔线、公式块、引用块等块级语法，通常需要空一行。

推荐写法：

```markdown
**核心结论**

模型真正有效的地方在于 POI 与 region 的解耦建模。
```

如果后面接分隔线：

```markdown
**核心结论**

---

下一节内容。
```

## 7. 标题、引用、分隔线、加粗、列表可以正常使用，但必须服务于语义

允许使用：
- `#` / `##` / `###`：标题层级；
- `>`：引用原文或突出重要总结；
- `---`：明确需要章节分隔时；
- `**...**`：强调关键词或结论；
- `-`：列表；
- `$...$` 和 `$$...$$`：公式。

使用这些符号时，需要检查它们是否会影响相邻内容的渲染。特别是引用块、公式块、分隔线、列表结束后，通常都需要用空行明确结束当前语法块。

## 8. 输出前检查

生成最终 Markdown 前，需要检查：
- 引用块 `>` 结束后是否空了一行；
- 分隔线 `---` 前后是否都有空行；
- 公式块 `$$...$$` 前后是否都有空行；
- 公式块内部是否保持纯 LaTeX；
- 列表内部是否过度空行；
- 列表结束后是否空一行再写正文；
- 是否存在 Markdown 控制符紧贴导致的误渲染；
- 是否有公式被错误地接在标题、引用或列表符号后面；
- 是否有加粗符号没有闭合。

# Obsidian 可读性标记与写作风格

这一部分用于解决另一个常见问题：为了避免 Markdown 误渲染，模型可能会过度保守，导致笔记只剩普通段落和列表，缺少层次感。论文阅读笔记可以合理使用加粗、斜体、高亮、引用块和 Obsidian callouts，但必须控制数量，并保证它们服务于语义区分。

核心原则是：

> Markdown 标记不是装饰，而是用来区分信息来源、重要程度和理解层次。


## 模型流程中个人理解的引用块规则

在 `# 3. 模型流程说明` 中，很多模块小节最后通常会加入一句或几句个人理解、总结判断、复现提醒或迁移启发。这类内容不应全部写成普通正文，否则在 Obsidian 中不容易与论文原始方法描述区分。

因此，在模型方法说明部分，建议遵循以下规则：

- 如果是**论文原始方法描述**，使用普通正文或列表说明。
- 如果是**个人理解、总结性判断、模块作用概括、值得注意的设计点**，优先使用引用块 `>` 进行凸显。
- 如果是**较强的迁移启发、复现风险、疑问**，可以进一步使用 Obsidian callout，例如 `[!tip]`、`[!warning]`、`[!question]`。
- 一个小节中如果只有一句简短个人理解，使用普通引用块即可，不必每次都使用 callout。
- 引用块结束后必须空一行，再继续普通正文，避免 Obsidian 将后续内容继续渲染为引用块。

推荐写法：

```markdown
## 3.3 Time-Interval Hypergraph

这个模块的目标是根据用户历史访问中的最小正时间间隔，构建 POI 之间的时间可达关系。对于用户 $u$，文章先计算用户访问过的 POI 集合 $V_u$ 内任意两个 POI 之间的最小正时间间隔，然后将存在时间可达关系的 POI 连接到同一个 hyperedge 中。

时间可达矩阵定义为：

$$
B_{ij}^{\Delta t,u}
=
\begin{cases}
1, & D_{ij}^{\Delta t} > 0 \\
0, & otherwise
\end{cases}
$$

其中，$D_{ij}^{\Delta t}$ 表示 POI $i$ 到 POI $j$ 之间的最小正时间间隔。

> 个人理解是，这里的重点不是精确预测两个 POI 之间需要多久，而是用“历史上是否存在可达迁移”构造一个时间约束下的高阶结构。它相当于把时间间隔从普通数值特征提升成了结构先验。
```

不推荐写法：

```markdown
## 3.3 Time-Interval Hypergraph

这个模块的目标是根据用户历史访问中的最小正时间间隔，构建 POI 之间的时间可达关系。

个人理解是，这里的重点不是精确预测两个 POI 之间需要多久，而是用“历史上是否存在可达迁移”构造一个时间约束下的高阶结构。
```

原因是第二种写法中，个人理解和论文原始方法描述混在一起，视觉层次不明显；第一种写法能够更清楚地区分“论文怎么做”和“我如何理解”。

### 引用块与 callout 的使用边界

普通引用块 `>` 适合用于轻量个人理解，例如：

```markdown
> 个人理解是，这一步本质上是在为 POI 表示加入用户局部轨迹中的结构约束，而不是学习全局 POI 图。
```

Obsidian callout 适合用于更强的提示，例如：

```markdown
> [!tip] 迁移启发
> 这个结构可以迁移到用户-region-category 偏好建模中，将用户在某个 region 内的类别共现关系构造成局部 hyperedge。
```

```markdown
> [!warning] 复现风险
> 论文这里将 candidate set 限制在用户历史访问过的 $V_u$ 中，这会显著降低预测难度。复现实验或与其他 next-POI 方法对比时，需要特别注意候选集设定是否一致。
```

整体原则是：

> 普通方法描述用正文；个人理解和总结判断用 `>`；重要启发、风险和疑问再升级为 callout。

## 1. 可以合理使用的标记类型

允许在论文笔记中使用以下标记：
- **加粗**：用于强调模块名、核心概念、关键结论、消融变体名称。
- *斜体*：用于标记英文术语、论文原文概念名、较轻量的语义强调。
- ==高亮==：用于标记非常值得回看、可能影响自己模型设计的重点结论。
- `>` 引用块：用于放置论文原始观点、作者明确表述的核心判断，或个人总结式判断。
- Obsidian callouts：用于区分“个人理解”“注意事项”“风险”“启发”“疑问”等解释性内容。

不要因为担心渲染问题而完全不使用这些标记。正确做法是 **少量、稳定、语义明确地使用**。

## 2. 加粗、斜体和高亮的使用规则

加粗适合用于强调稳定概念，例如模块名、任务名、关键机制：

```markdown
**Hyper Fusion Layer** 的作用不是简单拼接特征，而是根据当前 trip 动态生成融合权重。
```

斜体适合用于英文术语或轻量强调：

```markdown
这里的 *position embedding* 表示 trip 中的访问顺序，而不是 POI 的地理位置。
```

高亮适合用于最值得回看的结论，不要大面积使用：

```markdown
==这篇文章真正值得借鉴的是 POI-time 和 POI-position 的对齐式辅助任务，而不是 Transformer 本身。==
```

使用限制：
- 每个小节中高亮最好不超过 1 到 2 处。
- 不要整段高亮。
- 不要把公式放进高亮中。
- 不要让加粗或高亮跨越公式块、列表块或 callout 块。

## 3. 引用块的使用规则

引用块适合用于突出“论文原始观点”或“总结性判断”。引用块结束后必须空一行，再继续正文。

推荐写法：

```markdown
> 这篇文章的核心观点是：trip recommendation 不只是预测 POI 集合，还要保证访问时间和访问顺序的合理性。

个人理解是，这个观点对应到模型设计上，就是不能只把 time 和 position 当作普通特征拼接。
```

不推荐写法：

```markdown
> 这篇文章的核心观点是：trip recommendation 不只是预测 POI 集合。
个人理解是，这个观点对应到模型设计上……
```

引用块不要用于长篇正文。一般一段引用块控制在 1 到 3 行。

## 4. Obsidian callouts 的使用场景

Obsidian callout 本质上是带特殊标识的引用块，格式如下：

```markdown
> [!note] 标题
> 内容。
```

论文阅读笔记中建议使用以下几类 callout：

### 4.1 `[!note]`：用于论文原始设定或客观说明

适合放任务定义、作者设定、实验设置中需要额外提醒但不适合打断正文的内容。

```markdown
> [!note] 论文设定
> 这里的 query 包含起点、终点、起止时间和 trip 长度，因此它不是普通 next-POI prediction，而更接近 trip completion。
```

### 4.2 `[!tip]`：用于个人理解或迁移启发

适合放与自己研究相关的启发、可迁移模块、可能的改造方向。

```markdown
> [!tip] 个人理解
> 这个对比学习任务可以迁移到 next-POI recommendation 中，用来约束 POI 与 time bucket、region 或 category 的匹配关系。
```

### 4.3 `[!warning]`：用于复现风险、信息泄漏或公平性问题

适合放潜在问题，例如目标时间使用、ground-truth 输入、训练推理不一致、负样本构造不清晰等。

```markdown
> [!warning] 需要注意
> 如果训练阶段直接输入完整 ground-truth POI 序列，再预测同一序列，需要检查是否存在信息泄漏。
```

### 4.4 `[!question]`：用于论文没有讲清楚的问题

适合记录论文描述不充分、复现时需要确认、后续可能追代码的问题。

```markdown
> [!question] 复现疑问
> 论文没有明确说明推理阶段中间位置的 POI embedding 如何构造：是 mask token、占位 token，还是迭代生成？
```

### 4.5 `[!summary]`：用于小节结论

适合在某个大模块结束后，用 2 到 4 行总结关键机制。

```markdown
> [!summary] 小结
> Hyper Fusion Layer 解决的是动态融合问题，Dual-aspect Contrastive Learning 解决的是 POI 与时间、顺序位置的结构对齐问题。
```

## 5. Callout 使用数量控制

Callout 可以提升可读性，但不能过度使用。建议：
- `# 0. 实验` 中最多使用 1 个 callout，通常用于总结消融结论。
- `# 1. 论文核心问题` 中最多使用 1 个 callout，通常用于突出核心问题总结。
- `# 2. 论文贡献` 中通常不使用 callout，保持忠实原文。
- `# 3. 模型流程说明` 中可以使用 2 到 4 个 callout，用于个人理解、复现风险、关键小结。
- 整篇笔记总 callout 数量建议控制在 3 到 6 个。

不要每个小节都使用 callout。callout 应该只放真正需要被视觉区分的信息。

## 6. Callout 与公式块的边界规则

Callout 内可以写行内公式，例如 `$H_p$`、`$H_t$`，但不推荐在 callout 内放复杂独立公式块。

如果必须在 callout 后写公式，应先结束 callout，空一行后再写公式块。

推荐写法：

```markdown
> [!tip] 个人理解
> 这一步可以理解为为每个 trip 生成一个轻量级定制化融合层。

动态融合权重可以表示为：

$$
W_{hf}
=
W_{all}
+
W^*
$$

其中，$W_{all}$ 是共享参数，$W^*$ 是动态生成参数。
```

不推荐写法：

```markdown
> [!tip] 个人理解
> 动态融合权重可以表示为：
> $$
> W_{hf}=W_{all}+W^*
> $$
```

原因：在 Obsidian 中，callout 本身依赖引用块语法 `>`，如果在其中嵌入复杂公式块，容易造成公式块边界和引用块边界混淆。

## 7. 用标记区分三类内容

论文阅读笔记中建议明确区分三类内容。

第一类是 **论文原始内容**，主要用普通正文、列表和少量加粗表示：

```markdown
作者提出 Dual-aspect Contrastive Learning，包括 **POI Time-aware Contrastive Learning** 和 **POI Sequence-aware Contrastive Learning**。
```

第二类是 **解释性个人理解**，可以用 `[!tip]` 或“个人理解是”开头：

```markdown
> [!tip] 个人理解
> 这里的 contrastive learning 不是为了替代主任务，而是为了让 POI embedding 与 time / position embedding 在表示空间中形成更稳定的对应关系。
```

第三类是 **值得关注的风险或疑问**，可以用 `[!warning]` 或 `[!question]`：

```markdown
> [!warning] 需要注意
> 如果方法部分使用完整 $P$ 和 $T$ 作为输入，需要进一步确认训练和推理阶段是否一致。
```

这样可以让笔记读起来更像“研究笔记”，而不是单纯的论文翻译。

## 8. 推荐的写作风格

推荐整体风格是：
- 普通正文负责解释主干逻辑；
- 加粗负责标出核心概念；
- 高亮只标最重要结论；
- 引用块负责突出论文观点或总结；
- callout 负责承载个人理解、注意事项、复现疑问和迁移启发；
- 公式块保持干净独立，不被任何 Markdown 标记包裹。

写作时可以适度使用如下表达：
- **作者原文逻辑是**：……
- **个人理解是**：……
- ==这里最值得注意的是……==
- > [!tip] 对自己模型的启发
- > [!warning] 复现时需要注意
- > [!question] 论文没有讲清楚的地方

## 9. 输出前的可读性检查

生成最终笔记前，除了检查公式格式，还需要检查可读性标记：
- 是否完全没有使用加粗、引用、高亮或 callout，导致笔记层次不清。
- 是否过度使用高亮，导致重点失效。
- 是否每个 callout 都有明确用途。
- callout 后是否空一行再回到普通正文。
- callout 内是否嵌入了复杂独立公式块。
- 加粗、高亮、斜体是否都已正确闭合。
- 是否用 `[!warning]` 标出了可能影响复现或公平比较的关键问题。
- 是否用 `[!tip]` 或“个人理解”标出了对自己研究有启发的部分。

# 模型流程说明中的 Callout 嵌入规则

这一部分是对前面“Obsidian 可读性标记与写作风格”的进一步细化。Callout 不应该只集中放在最后的 `## 3.8 个人理解与值得注意的关键点` 中。更推荐的做法是：在 `# 3. 模型流程说明` 的具体模块分析小节中，按需嵌入 callout，用来帮助读者快速理解复杂模块的做法、内核原理、复现风险和迁移启发。

核心原则是：

> Callout 应该出现在读者最需要被提醒的位置，而不是全部堆到最后总结部分。

## 1. Callout 的优先放置位置

在论文阅读笔记中，callout 的优先放置位置应为：
1. `## 3.3`、`## 3.4`、`## 3.5` 等具体模块分析小节；
2. 某个复杂公式或流程解释之后；
3. 某个容易误解的模块输入、输出或训练方式旁边；
4. 某个存在复现风险或信息泄漏风险的步骤旁边；
5. 某个对自己研究有直接启发的机制旁边。

`## 3.8 个人理解与值得注意的关键点` 仍然可以保留，但它的作用应该是做整体综合，不应该成为 callout 的唯一集中区域。

## 2. 模块分析小节中的推荐 callout 类型

### 2.1 `[!summary] 模块速读`

用于在复杂模块开头或模块流程讲完后，用 2 到 4 行快速概括该模块到底做了什么。

推荐位置：模块小节开头的第一段解释之后，或者模块流程说明结束后。

```markdown
> [!summary] 模块速读
> 这个模块的核心是根据当前 trip 的 POI-time 表示动态生成融合层参数，因此它不是普通的 concat + linear，而是让每条 trip 拥有一个轻量级的个性化融合函数。
```

### 2.2 `[!tip] 个人理解`

用于解释模块的内核原理、为什么这样设计、这个设计和普通做法的区别。

推荐位置：公式或流程解释之后，而不是小节最后统一堆叠。

```markdown
> [!tip] 个人理解
> 这里真正起作用的不是多引入了一个 time embedding，而是让 POI 与 time 的匹配关系参与参数生成，从而改变特征融合方式。
```

### 2.3 `[!warning] 需要注意`

用于标记训练/推理不一致、target time 使用、ground-truth 输入、mask 策略、负样本构造、评价公平性等风险。

推荐位置：紧跟在对应风险步骤之后。

```markdown
> [!warning] 需要注意
> 如果训练阶段直接输入完整 ground-truth POI 序列，再预测同一序列，需要进一步确认是否存在信息泄漏，以及推理阶段中间位置如何构造输入。
```

### 2.4 `[!question] 复现疑问`

用于记录论文没有讲清楚、需要查代码或实验设置才能确认的问题。

推荐位置：论文描述模糊的模块说明之后。

```markdown
> [!question] 复现疑问
> 论文没有明确说明负样本是 batch 内打乱、序列内打乱，还是额外采样得到；这会影响 contrastive loss 的实现方式和训练复杂度。
```

### 2.5 `[!example] 直观例子`

用于在复杂模块之后给出一个简短例子，帮助理解该模块的行为。

推荐位置：抽象模块解释之后。

```markdown
> [!example] 直观例子
> 如果一个 POI 更常在晚上被访问，而打乱后被配到了上午时间，那么 POI Time-aware Contrastive Learning 会把这种错误匹配视为负样本。
```

## 3. 不同模块适合使用的 callout

在 `# 3. 模型流程说明` 中，可以按照模块性质选择 callout：

| 模块类型 | 推荐 callout | 用途 |
|---|---|---|
| 输入与任务定义 | `[!warning]` / `[!question]` | 标记任务设定、训练推理差异、是否使用目标信息 |
| Embedding 层 | `[!summary]` / `[!tip]` | 快速说明每类特征的含义，区分 ID、time、position、category 等 |
| 图模块 / KG 模块 | `[!summary]` / `[!tip]` / `[!warning]` | 概括构图方式、揭示传播逻辑、提醒归一化或信息泄漏风险 |
| Transformer / RNN / Attention 模块 | `[!summary]` / `[!tip]` | 概括序列建模逻辑，解释 attention 或 hidden state 的作用 |
| 对比学习 / 辅助任务 | `[!tip]` / `[!question]` / `[!example]` | 解释正负样本构造、辅助目标的作用、实现不清楚之处 |
| 预测与融合 | `[!warning]` / `[!summary]` | 标记 score-level fusion、target time、候选集过滤、分类头共享等关键点 |
| Loss 设计 | `[!summary]` / `[!warning]` | 概括多任务 loss 组成，提醒 loss 权重和监督信号来源 |

## 4. Callout 不应只放在最后总结

不推荐的写法是：前面所有模块都用普通正文堆叠，直到 `## 3.8 个人理解与值得注意的关键点` 才连续放多个 callout。这样虽然结构整齐，但读者在阅读复杂模块时无法及时获得提示。

不推荐结构：

```markdown

长段模块说明……

## 3.4 Transformer Layer

长段模块说明……

> 关于 Hyper Fusion Layer 的理解……

> [!warning] 需要注意
> 关于 Transformer 输入的风险……
```

```markdown

长段模块说明……

> [!summary] 模块速读
> Hyper Fusion Layer 的核心是根据当前 trip 动态生成融合权重，使 POI-time 融合从静态函数变成样本自适应函数。
```

## 5. Callout 的数量分布建议

整篇笔记 callout 总量仍然需要控制，但应优先分布在模块分析部分：
- `# 0. 实验`：0 到 1 个，通常用于消融结论。
- `# 1. 论文核心问题`：0 到 1 个，通常用于核心问题总结。
- `# 2. 论文贡献`：通常不用 callout，保持忠实原文。
- `# 3. 模型流程说明`：建议使用 3 到 6 个 callout，并尽量放在具体模块小节中。
- `## 3.8 个人理解与值得注意的关键点`：最多 0 到 1 个 callout，更多使用普通段落总结即可。

如果某篇文章模型结构非常复杂，可以适度增加到 6 到 8 个 callout，但必须保证每个 callout 都有明确功能，不要为了装饰而使用。

## 6. 模块内 callout 的写作要求

模块内 callout 应该满足：
- 标题明确，例如“模块速读”“个人理解”“需要注意”“复现疑问”“直观例子”。
- 内容短，通常 2 到 4 行。
- 只解释一个点，不要把多个模块的理解混在一个 callout 里。
- 不重复正文已经说清楚的内容，而是压缩、提炼或提醒。
- 尽量靠近它所解释的公式、步骤或模块，而不是延后到全文结尾。

## 7. 与公式块的关系

模块内 callout 可以出现在公式块前或公式块后，但不要包裹复杂公式。

推荐写法：

```markdown
Hypernetwork 生成的动态参数与全局共享参数相加：

$$
W_{hf}
=
W_{all}
+
W^*
$$

> [!tip] 个人理解
> 这里可以理解为“共享基础融合能力 + 当前 trip 的个性化参数偏移”，因此它比完全静态的线性融合更灵活。
```

不推荐写法：

```markdown
> [!tip] 个人理解
> Hypernetwork 的参数为：
> $$
> W_{hf}
> =
> W_{all}
> +
> W^*
> $$
```

```markdown
> [!summary] 模块速读

其中，$x$ 表示……，$y$ 表示……。
```

## 9. 对 `## 3.8` 的定位调整

`## 3.8 个人理解与值得注意的关键点` 不再承担“集中放置所有个人理解和 callout”的功能。它应该改为：
- 总结整篇模型真正有效的机制；
- 串联不同模块之间的关系；
- 说明对自己研究方向的整体启发；
- 简要列出 1 到 3 个最重要的复现风险。

如果前面模块内已经使用了 callout，`## 3.8` 中可以不再使用 callout，或只使用一个 `[!summary] 总体理解`。

# 最终交付方式建议

这一部分用于解决一个实际问题：如果 AI 直接在聊天回答中输出完整 Markdown，聊天窗口可能会对标题、公式、引用块、callout、代码块进行二次渲染，从而导致复制到 Obsidian 后出现格式错乱。因此，较长论文笔记应优先选择更稳定的交付方式。

## 1. 首选：直接生成 `.md` 文件

当论文阅读笔记较长、包含大量公式、包含多个 callout、或者用户明确要求适合 Obsidian 使用时，首选交付方式是生成 `.md` 文件。

推荐做法：
- 在聊天中只给简短说明；
- 提供 `.md` 文件下载链接；
- 不在聊天窗口中完整粘贴整篇笔记；
- 文件内部严格保留 Markdown 原文结构。

推荐回复方式：

```markdown
我已生成 Obsidian 兼容 Markdown 文件，你可以直接下载使用：

[下载论文阅读笔记](sandbox:/mnt/data/xxx.md)
```

这样最稳定，因为 `.md` 文件不会被聊天窗口的 Markdown 渲染层改写。

## 2. 次选：用代码块输出完整 Markdown

如果用户不方便下载文件，或者明确要求“直接把内容贴出来”，可以用代码块输出完整 Markdown。代码块可以减少聊天窗口对 Markdown 的二次渲染，使用户复制时更接近原始文本。

但是需要注意：
- 代码块输出适合中短篇内容；
- 超长笔记放进代码块会很难复制和检查；
- 如果笔记内部本身包含代码块，容易出现三反引号嵌套问题；
- 代码块中的内容不会在聊天窗口中预览真实排版，只适合作为“原始 Markdown 文本”复制。

推荐说明：

```markdown
下面用代码块给出原始 Markdown，复制到 Obsidian 后再查看渲染效果。
```

## 3. 不推荐：长篇笔记直接作为普通聊天内容输出

如果完整笔记直接作为普通聊天 Markdown 输出，可能出现以下问题：
- `$$` 公式块被聊天窗口提前渲染或截断；
- `# $$`、`> $$`、`- $$` 等错误更难被发现；
- callout 的 `>` 引用边界可能影响后续正文；
- 列表、引用块、公式块之间的空行可能被视觉上弱化；
- 用户复制时可能复制到已经被渲染后的内容，而不是原始 Markdown。

因此，长篇论文笔记尤其是公式较多时，不要优先采用普通聊天输出。

## 4. 推荐决策规则

生成论文阅读笔记时，按下面规则选择交付方式：
- **长篇笔记 + 多公式 + Obsidian 格式要求**：直接生成 `.md` 文件。
- **用户要求可直接复制，且内容不长**：可以使用代码块输出原始 Markdown。
- **用户要求边看边改、逐段讨论**：可以在聊天中分小节输出，但每次只输出一个模块，并保持公式块边界安全。
- **用户没有明确要求展示全文**：默认生成 `.md` 文件，并在聊天中给出简短说明。

## 5. 推荐提示词补充

用户可以在请求中直接加入：

```markdown
请优先生成 `.md` 文件给我下载，不要在聊天窗口中直接输出完整正文；如果必须展示正文，请用代码块输出原始 Markdown，避免聊天窗口二次渲染导致 Obsidian 公式或 callout 格式错乱。
```

## 6. 与公式安全规则的关系

交付为 `.md` 文件并不意味着可以放松公式检查。无论是 `.md` 文件、代码块输出，还是普通聊天输出，都必须满足：
- `$$` 单独占一行；
- 公式块前后空行；
- 公式块内部只包含 LaTeX；
- 不出现 `# $$`、`> $$`、`- $$`、`* $$`、`+ $$`；
- callout 不包裹复杂独立公式；
- 不用代码块包裹正式笔记正文，除非用户明确要求“用代码块给出原始 Markdown”。

# Obsidian 公式渲染防错强约束

这一部分用于避免公式在 ChatGPT 聊天窗口或 Obsidian 中被错误渲染，尤其是避免出现 `# $$`、`> $$`、`- $$`、公式标识符错位、正文被误放入代码块等问题。

## 1. 最终交付优先使用 `.md` 文件

如果阅读笔记较长，尤其是包含大量公式时，优先将最终笔记生成并交付为 `.md` 文件，而不是只在聊天窗口中直接输出完整正文。

推荐交付方式：


独立公式块的开始和结束标识符必须各自单独占一行，行内不能出现标题、引用、列表、加粗、空格以外的其他字符。

```markdown
\left(

\right)
```

禁止写法：


禁止写法：

公式块内部禁止出现以下内容：
- 标题符号：`#`

- 加粗符号：`**`

在输出最终笔记前，必须检查以下规则：

- 不存在 `# $$`。
- 不存在 `## $$`。
- 不存在 `### $$`。

- 不存在 `- $$`。

## 8. 推荐的生成流程

长篇论文阅读笔记建议采用下面流程：

1. 先核实发表信息、等级、指标与代码状态，整理开头论文信息块和四部分正文结构。
2. 将最终笔记写入 `.md` 文件。
3. 对 `.md` 内容执行论文信息块输出检查和公式块安全检查。
4. 如果发现 `# $$`、`> $$`、`- $$`、未闭合 `$$`、代码块包裹正文等问题，先修复再交付。
5. 最终优先给出 `.md` 下载链接，而不是直接把长篇 Markdown 全部贴在聊天窗口中。

```markdown
请你按照我的论文阅读笔记 skill，帮我写这篇论文的阅读笔记。

要求：
1. 笔记开头先添加论文信息块，正文固定为 4 个部分：0.实验，1.论文核心问题，2.论文贡献，3.模型流程说明。期刊填写名称、JCR 分区、中科院分区、JIF 与代码公开状态；会议填写名称、轨道、CCF 分级、顶会认定与代码公开状态。联网核实等级和指标并注明数据年份、版本与来源，代码公开则给出官方地址，无公开代码写否；论文声明开源但仓库不可用或找不到时注明情况，无法核实则说明原因，记录查询日期。
2. 实验部分只说明消融实验，包括消融内容、个人理解式结论和值得注意的地方，不展开主实验、超参数和效率实验。
3. 论文核心问题部分说明文章解决什么问题，不要写成模型流程。
4. 论文贡献部分主要翻译整理引言中的贡献点。
5. 模型流程说明要清晰详细，包括输入特征、各组件、预测方式、loss，以及必要的个人理解。
6. 模型流程中的公式、变量、矩阵、loss 和数据 pipeline 使用 Obsidian 适配格式：行内公式用 `$...$`，独立公式用 `$$...$$`。
7. 独立公式块的 `$$` 必须单独占一行，且前后必须空行；绝对不要出现 `# $$`、`> $$`、`- $$`、`* $$`、`+ $$`。
8. 公式块内部只能包含 LaTeX，不能放标题、引用、列表、加粗、分隔线或普通正文。
9. 不要用代码块包裹整篇阅读笔记；如果内容较长或公式较多，优先生成 `.md` 文件给我下载。
10. Markdown 输出采用紧凑排版：列表项之间不要插入空行，不要每句话都拆成单独段落。
11. 输出前检查公式块是否成对闭合，是否存在 Markdown 控制符紧贴公式块的问题。
```

# 追加后的可直接复用提示词补充

如果希望笔记可读性更强，可以在原提示词后追加：

```markdown
12. 写作风格不要过度保守，可以适量使用加粗、斜体、高亮、引用块和 Obsidian callouts 来区分论文原始内容、个人理解、重点提醒、复现风险和迁移启发。
13. 加粗用于核心概念和模块名；斜体用于英文术语或轻量强调；高亮只用于最值得回看的关键结论，整篇不要过度使用。

15. callout 内可以使用行内公式，但尽量不要放复杂独立公式块；复杂公式应放在 callout 外，并保证 `$$` 单独占一行。
16. 公式块仍然必须保持最高优先级的渲染安全：不要出现 `# $$`、`> $$`、`- $$`，公式块内部只能包含 LaTeX。
```
